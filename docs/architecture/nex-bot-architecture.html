1 总体架构

四层：客户端 → Core → 外部服务 / 设备。Core 是唯一的业务中心，客户端不保存业务逻辑。

核心决策（core-service-thin-shell.md）：主设备不再是 Electron 应用，而是一个后端部署；所有桌面包都是同一种“瘦壳”，没有 Core、worker、本地数据库或 UI 业务包，关闭客户端不会影响 Core。

2 Core 内部模块

位于 server/personal-os/，约 680 个文件（含测试）。

身份账号与工作区

  • identity*.ts、identity-schema.sql
  • workspaces.ts：账号工作区，Core ID 稳定
  • clients.ts / devices.ts：登录设备
  • 对接 nex_user，业务/任务/工具边界反复校验

执行Agent 运行

  • runtime.ts：fork worker，按助手限制并发，给后台维护留一个空位
  • worker.ts：基于 @earendil-works/pi-coding-agent
  • contracts.ts：Core 与 worker 的消息协议
  • tool-catalog.ts：常用工具 + 按需发现

上下文对话与压缩

  • projection*.ts：对话投影
  • episodes*.ts、context-tools.ts
  • compaction-*.ts：压缩时机与失败处理
  • conversation-search：对话检索

记忆多层记忆

  • memory*.ts、core-memory.ts
  • topic-tree*、topic-access*：话题树与访问隔离
  • retrieval*、embeddings、rerank
  • hindsight.ts：外部记忆插件

功能产品能力

  • todos*：待办，可交给助手并验收
  • routines*：例行任务，独立执行
  • skills.ts、connectors*
  • gmail-*、feishu

安全策略与审批

  • policy.ts：evaluateTool 判定
  • risk.ts、approval-rules.ts
  • broker-tool.ts：worker 的审批代理工具
  • 可记住的审批规则

4 设备执行（DCP）

来自 docs/verification/client-device-executor.md。命令在用户电脑上执行，但助手本身跑在 Core。

这条通道的特点：一次命令对应一次结果返回（stdout 约 50KB、stderr 约 10KB 的截断，见 node.ts），没有长连接的事件流。所以它适合“让助手执行命令”，不适合直接承载另一个 agent CLI 的对话流（见第 8 节）。

8 让 nex_bot 操作本机 CLI 的方案（历史快照）

本节保留 2026-11-03 的方案记录。当前已通过设备端 device.agent 实现 Codex 和 Claude CLI 的发现、启动、续接、审批和停止，支持 Windows 与 macOS；实现和验证见 本机 Agent CLI 验证记录。

上游做法：每个 CLI 一个 driver，起子进程并通过 stdio 通信；用 broker 转发权限审批。
